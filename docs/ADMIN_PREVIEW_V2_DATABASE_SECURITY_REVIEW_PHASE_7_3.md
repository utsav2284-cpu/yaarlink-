## Platform facts verified against official documentation

| Claim used in the design | Verification | Source |
|---|---|---|
| JWTs carry `aal` (`aal1`/`aal2`), `session_id`, and `amr` entries `{method,timestamp}` with methods including `password`, `totp`, `recovery`, `invite`, `token_refresh` | **Verified** — `aal2` alone does not prove the factor type; the `amr` `totp` timestamp is the token-visible evidence of last TOTP verification | https://supabase.com/docs/guides/auth/jwt-fields |
| TOTP enroll → challenge → verify upgrades the session; assurance API distinguishes current/next level and can expose a stale AAL2 token after factor removal | **Verified** | https://supabase.com/docs/guides/auth/auth-mfa/totp |
| Unenrolling a verified factor requires an AAL2 session; verifying a factor logs out other sessions | **Verified** (JS reference) | https://supabase.com/docs/reference/javascript/auth-mfa-enroll |
| `signOut` scopes are `local` / `global` (JS default) / `others`; sign-out revokes refresh tokens but **access tokens remain valid until `exp`** | **Verified** — this is why the local session registry is the immediate authorization barrier | https://supabase.com/docs/guides/auth/signout |
| A supported Admin API to delete one arbitrary session of another user **by session ID** | **Not verified / not assumed.** The design therefore never relies on it; single-other-session revocation is enforced through the registry + RLS (§20.5 of the design) | — |
| An Auth webhook/event guaranteed to fire on factor removal | **Not assumed.** Factor state is re-checked live on privileged requests instead | — |
| PostgreSQL transactional DDL and advisory transaction locks (`pg_advisory_xact_lock`) for audit-chain serialization | Standard PostgreSQL behaviour relied upon for §§13/20.4 | https://www.postgresql.org/docs/current/explicit-locking.html |

Everything not listed as verified above is labelled an assumption or a limitation in the design.

## Preserved Phase 7.1 requirements (regression check)

Session currency in RLS, definer-function lockdown (revoked default grants, empty `search_path`, in-function authorization, atomic audit), bootstrap atomic conditional update, audit role separation, recovery-code hardening (argon2id + pepper, atomic use, lockout, no AAL2 equivalence), typed report FKs, cascade prohibitions, synthetic-data framing, Auth telemetry blind-spot, and the four open Phase 6 items (Site URL/redirects, password policy, AAL2 *implementation*, first-owner creation) are all still present and unweakened; Phase 7.3 strengthens the bootstrap, step-up, and audit items and corrects the contradictions above.

## Test strategy

The future (implementation-phase) test specification was expanded to the 20 mandated cases — concurrent bootstrap, invalid/no-invitation and no-MFA bootstrap, duplicate acceptance, Auth/DB partial-failure retry, AAL1 direct-API access, stale-AAL2-after-factor-removal, fresh-TOTP step-up, step-up replay and cross-session use, revoked-JWT PostgREST replay, individual/global revocation, concurrent audit writes, audit modification/deletion attempts, full-chain tamper vs checkpoint verification, expired-role reassignment, concurrent grants/revocations, last-owner protection, service-role misuse, and column-level exposure (design §20.9). No test was executed in this phase.
